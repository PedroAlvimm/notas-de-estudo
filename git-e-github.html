1. Fluxo de Trabalho no GitHub

Pág. 1/2

1.1O que é Git?

  • Git é um sistema de controle de versão distribuído: guarda o histórico de cada mudança no código.
  • Cada pessoa tem uma cópia completa do repositório, com todo o histórico, no próprio computador.
  • Commit = uma "foto" do projeto com mensagem, autor, data e um hash (ex.: a1b2c3d).
  • Branch = uma linha de trabalho paralela. Você testa ideias sem mexer na main.

1.2Git vs GitHub

  • Git: a ferramenta. Roda no seu PC, pela linha de comando.
  • GitHub: site que hospeda repositórios Git e adiciona colaboração: Pull Requests, Issues, Actions (CI/CD).

1.3As 4 áreas do Git

Dica: git status mostra em qual área cada arquivo está. git restore --staged arq tira um arquivo da staging.

O que cada comando faz

ComandoO que fazMexe nos seus arquivos?
git cloneCopia o repositório inteiro do GitHub, na primeira vez.Cria a pasta
git fetchSó baixa os commits novos do GitHub e atualiza o origin/main. Sua branch fica como estava.Não
git mergeJunta outra branch na branch em que você está. Ex.: git merge origin/main traz o que o fetch baixou.Sim
git pullfetch + merge num comando só.Sim
git pushEnvia os seus commits para o GitHub.Não, só o GitHub
  • origin/main é a cópia, no seu computador, de como a main estava no GitHub no último fetch. Ela não muda sozinha.
  • Por que usar fetch: é seguro. Você vê o que chegou com git log main..origin/main e só depois decide fazer o merge.

Os dois jeitos de um merge acontecer

  • Fast-forward: a main não mudou desde que a branch saiu dela. O Git só move a main para frente.
  • Commit de merge: as duas andaram. O Git cria um commit novo que junta as duas histórias.
  • Se as duas mudaram a mesma linha, o merge para e pede ajuda: é um conflito (seção 1.12).

1.4GitHub Flow em um olhar

Regra de ouro: a main está sempre pronta para ir para produção. Todo trabalho novo nasce numa branch.

1.5Passo a passo

  1. Atualize: git clone <url> (1ª vez) ou git pull
  2. Crie a branch: git switch -c feature/login
  3. Edite e salve: git add . e git commit -m "feat: tela de login"
  4. Envie: git push -u origin feature/login
  5. Abra o Pull Request no GitHub explicando o que mudou e por quê.
  6. Review + CI: colegas comentam, os testes (Actions) precisam passar.
  7. Merge na main e apague a branch.
  8. Volte pra main: git switch main e git pull

1.6O que é um Pull Request?

  • PR = pedido para juntar sua branch na main: "revisem e incorporem minhas mudanças".
  • Mostra o diff: linhas adicionadas e removidas, arquivo por arquivo.
  • Colegas fazem o review: comentam linhas, pedem mudanças ou aprovam.
  • Novos commits na mesma branch entram sozinhos no PR, e os testes rodam de novo.
  • Ainda não terminou? Abra como Draft (rascunho). No GitLab o nome é Merge Request.

1.7Issues e Projects

  • Issue = tarefa, bug ou ideia, com um número (ex.: #12).
  • Organize com labels (bug, enhancement), assignees (responsável) e milestones (meta ou versão).
  • Escreva Closes #12 na descrição do PR: quando ele for aceito, a issue fecha sozinha.
  • Projects = quadro kanban (Todo → In Progress → Done) com issues e PRs.

Ciclo completo: issue #12 → branch → commits → PR "Closes #12" → testes ✓ → review → merge.

1.8GitHub Actions (CI/CD)

  • Roda tarefas automáticas a cada push ou PR: testes, lint, build, deploy.
  • Fica em .github/workflows/ci.yml:
name: CI on: [push, pull_request] jobs: test: runs-on: ubuntu-latest steps: - uses: actions/checkout@v4 - run: npm ci - run: npm test
  • O resultado aparece no PR: ✓ verde libera o merge, ✗ vermelho precisa corrigir.
  • CI = testar sempre. CD = publicar automaticamente.

1.9Fork: contribuir com projetos de outros

  1. Clique em Fork: cria uma cópia do repositório na sua conta.
  2. git clone do seu fork e crie uma branch.
  3. Ligue ao original: git remote add upstream <url>
  4. Mantenha atualizado com git fetch upstream e dê push no seu fork.
  5. Abra o PR do seu fork para o repositório original.

origin = o seu fork · upstream = o projeto original.

1.11Merge, Squash ou Rebase?

Botão do PRHistóricoQuando usar
Create a merge commitMantém todos os commits + 1 commit de merge.Quer o histórico fiel da branch.
Squash and mergeJunta a branch inteira em 1 commit.PRs pequenos, main limpa.
Rebase and mergeReaplica os commits em cima da main. Linha reta, sem commit de merge.Quer histórico linear e commits bem escritos.

Cuidado: não faça rebase de uma branch que outras pessoas já usam. Ele reescreve o histórico.

1.12Conflito de merge

Acontece quando duas branches mudam a mesma linha. O Git marca o trecho assim:

<<<<<<< HEAD const preco = 10; ← sua branch ======= const preco = 12; ← a que está chegando >>>>>>> feature/preco
  1. Escolha uma versão (ou combine as duas).
  2. Apague as linhas <<<, === e >>>.
  3. git add arquivo e git commit para concluir.

1.15Boas práticas

  • Commits pequenos e com mensagem clara: feat: fix: docs: (Conventional Commits).
  • Nunca commite direto na main. Ative branch protection no repositório.
  • Faça git pull antes de começar e antes do push.
  • Use .gitignore para não subir node_modules, .env e senhas.
  • PR pequeno é revisado mais rápido e quebra menos coisa.
  • Rode os testes localmente antes de pedir review.

2. Git no Dia a Dia

Pág. 2/2

2.1Primeiro dia: configuração e acesso

  1. Diga quem você é (aparece em todo commit):
    git config --global user.name "Pedro Alvim"
    git config --global user.email "seu@email.com"
  2. Use main como nome padrão: git config --global init.defaultBranch main
  3. Crie uma chave SSH: ssh-keygen -t ed25519 -C "seu@email.com" e cole o conteúdo do arquivo .pub em GitHub → Settings → SSH and GPG keys.
  4. Teste a conexão: ssh -T git@github.com

Atenção: desde 2021 o GitHub não aceita sua senha no push. Use SSH, um Personal Access Token ou faça login com gh auth login.

2.2Por que commitar numa branch separada?

  • A main fica sempre funcionando. O que está nela pode ir para produção a qualquer hora.
  • Você pode errar à vontade. Se a ideia não der certo, é só apagar a branch.
  • Trabalho em paralelo: várias pessoas (ou várias tarefas suas) andam sem pisar uma na outra.
  • Só com branch existe PR: review e testes acontecem antes de o código entrar na main.
  • Histórico organizado: cada branch é uma tarefa, fácil de achar e de desfazer.
  • Com branch protection ligada, o push direto na main é bloqueado.

2.3Commit numa branch separada, passo a passo

  1. Parta da main atualizada: git switch main e git pull
  2. Crie a branch e entre nela: git switch -c feature/cadastro
    (forma antiga: git checkout -b feature/cadastro)
  3. Confira onde está: git branch mostra um * na branch atual. O git status diz "On branch feature/cadastro".
  4. Trabalhe e commite normalmente: git add . e git commit -m "feat: formulário de cadastro". O commit vai para a branch, e a main não muda.
  5. Primeiro push da branch: git push -u origin feature/cadastro. O -u liga a branch local à do GitHub. Dali em diante, basta git push.
  6. Abra o PR: base: main ← compare: feature/cadastro.

Regra: o commit sempre vai para a branch onde o HEAD está. Troque de branch antes de commitar.

Ops! Mexi na main sem querer

Ainda não commitou? Rode git switch -c feature/x. As mudanças vão junto para a branch nova.

Já commitou, mas não deu push?

  1. git branch feature/x guarda o commit numa branch nova.
  2. git reset --hard origin/main volta a main ao estado do GitHub.
  3. git switch feature/x e siga trabalhando.

Antes do passo 2, confira no git status que não há mudanças sem commit. Se já deu push na main, não use reset: use git revert.

2.5Mantendo a branch atualizada

Enquanto você trabalha, a main recebe commits de outras pessoas. Traga essas mudanças para a sua branch:

Opção 1: merge (mais simples e seguro)

git fetch origin e git merge origin/main

Opção 2: rebase (histórico em linha reta)

git fetch origin e git rebase origin/main, depois git push --force-with-lease

  • Atualize com frequência: um conflito pequeno hoje é melhor que um gigante na sexta.
  • git pull --rebase evita commits "Merge branch..." à toa.

2.6Como desfazer erros

SituaçãoComandoRisco
Quero descartar mudanças num arquivo (sem commit)git restore arquivocuidado perde as mudanças do arquivo
Coloquei um arquivo na staging sem querergit restore --staged arquivoseguro
Errei a mensagem ou esqueci um arquivo no último commitgit add arquivo + git commit --amendseguro se ainda não deu push
Desfazer o último commit e manter as mudanças prontasgit reset --soft HEAD~1seguro mudanças ficam na staging
Desfazer o último commit e tirar da staginggit reset HEAD~1seguro arquivos ficam modificados
Jogar tudo fora e voltar a um commitgit reset --hard <hash>perigoso apaga o que não foi commitado
Desfazer um commit que já está no GitHubgit revert <hash>seguro cria um commit novo
"Perdi um commit!"git reflog e depois git switch -c resgate <hash>rede de segurança

Regra: depois do push, prefira revert. O reset e o --amend reescrevem o histórico e atrapalham quem já baixou o código.

2.7Segredos e segurança

  • Nunca commite senhas, tokens, chaves de API ou o .env. Coloque no .gitignore e suba um .env.example sem os valores.
  • Commitou sem querer? Apagar o arquivo não basta, porque a chave continua no histórico. Revogue a chave e gere outra na hora.
  • Nas Actions, guarde chaves em Secrets (Settings → Secrets and variables → Actions) e leia com ${{ secrets.API_KEY }}.
  • Secret scanning e push protection: o GitHub pode bloquear o push quando detecta uma chave conhecida.
  • Dependabot avisa sobre dependências com falha de segurança e abre PRs de atualização.
  • Ative a verificação em 2 etapas (2FA) na sua conta.

2.8Bom PR e code review

Um bom PR tem:

  • Título claro: feat: cadastro de usuário.
  • Descrição: o que mudou, por quê, como testar e prints se mexeu na tela.
  • Tamanho pequeno. Algumas centenas de linhas ainda dá para revisar com atenção.
  • Ligação com a issue: Closes #12.

No review, você escolhe:

  • Comment (só comentar), Approve (aprovar) ou Request changes (pedir mudanças).
  • Suggestion: propõe o código pronto no comentário, e o autor aceita com um clique.
  • Critique o código, não a pessoa, e explique o porquê.

2.10Ferramentas

  • GitHub CLI (gh): gh pr create, gh pr checkout 42, gh issue list. Faz PR sem sair do terminal.
  • GitHub Desktop: interface visual para commit, branch e push.
  • VS Code: aba Source Control com diff e botões para resolver conflitos (Accept Current, Incoming ou Both).
  • Tecla "." em qualquer repositório no GitHub abre um editor no navegador (github.dev).
  • Codespaces: ambiente de desenvolvimento completo na nuvem, já com o repositório aberto.
