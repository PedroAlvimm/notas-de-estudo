1. Fundamentos de Banco de Dados

Pág. 1/3

Exemplos em MySQL 8. A maior parte do SQL funciona igual no PostgreSQL, SQL Server e SQLite.

1.1O que é um banco de dados?

  • Banco de dados = conjunto organizado de dados, guardado de forma permanente e fácil de consultar.
  • SGBD (Sistema Gerenciador de Banco de Dados) = o programa que cuida dele: MySQL, PostgreSQL, SQL Server, Oracle, SQLite.
  • SQL (Structured Query Language) = a linguagem para criar, consultar e alterar os dados. Criada na IBM nos anos 70.
  • Num banco relacional, os dados ficam em tabelas que se ligam por chaves.
  • O SQL não diferencia maiúsculas de minúsculas, mas o costume é escrever os comandos em MAIÚSCULAS e os nomes em minúsculas.

1.2Relacional (SQL) vs NoSQL

AspectoRelacionalNoSQL

EsquemaDefinido antes (rígido)Flexível, muda por registro
RelaçõesJOINs entre tabelasDados aninhados ou duplicados
GarantiasTransações ACID fortesVaria: o MongoDB já tem transações, outros priorizam escala

Sistemas de pedidos, financeiro e cadastros costumam ir de relacional. Cache, logs e dados muito variáveis costumam ir de NoSQL.

1.6Chaves e restrições

  • PRIMARY KEY (PK): identifica cada linha. Única e nunca NULL. Uma por tabela, mas pode juntar várias colunas (chave composta).
  • FOREIGN KEY (FK): coluna que aponta para a PK de outra tabela. Impede pedido de cliente que não existe.
  • AUTO_INCREMENT: o banco gera o próximo número sozinho (1, 2, 3...).
  • NOT NULL: o campo é obrigatório.
  • UNIQUE: não deixa repetir valor (ex.: e-mail).
  • DEFAULT: valor usado quando nada é informado.
  • CHECK: regra de validação, como CHECK (valor > 0). Só é aplicado a partir do MySQL 8.0.16.

O que acontece com os filhos quando o pai some?

  • ON DELETE CASCADE apaga os pedidos junto com o cliente.
  • ON DELETE SET NULL deixa o pedido sem cliente.
  • ON DELETE RESTRICT bloqueia a exclusão. Sem nada escrito, o padrão (NO ACTION) faz o mesmo.
  • ON UPDATE CASCADE atualiza os filhos quando a chave do pai muda.

1.7Relacionamentos

  • 1:1 uma pessoa tem um CPF. Use FK + UNIQUE.
  • 1:N a FK fica do lado do "N" (pedidos.cliente_id).
  • N:N precisa de uma tabela associativa com as duas FKs.

1.8Normalização

Organizar as tabelas para não repetir dados e evitar inconsistência.

  • 1FN: cada célula guarda um valor só. Nada de "café, leite, pão" numa coluna: vira uma linha por produto.
  • 2FN: 1FN + toda coluna depende da chave inteira. Em chave composta (pedido_id, produto_id), o nome do produto vai para a tabela de produtos.
  • 3FN: 2FN + nenhuma coluna depende de outra coluna comum. Se o CEP define a cidade, a cidade sai da tabela de clientes.

Para lembrar: cada coluna depende "da chave, da chave inteira e de nada além da chave". Em relatórios pesados, às vezes se desnormaliza de propósito para ganhar velocidade.

2. SQL na Prática

Pág. 2/3

Todos os exemplos usam o mesmo banco: loja, com as tabelas clientes e pedidos.

2.1Criando a estrutura (DDL)

CREATE DATABASE IF NOT EXISTS loja
  CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
USE loja;

CREATE TABLE clientes (
  id        INT AUTO_INCREMENT PRIMARY KEY,
  nome      VARCHAR(100) NOT NULL,
  email     VARCHAR(150) UNIQUE,
  cidade    VARCHAR(60),
  criado_em DATETIME DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE pedidos (
  id         INT AUTO_INCREMENT PRIMARY KEY,
  cliente_id INT NOT NULL,
  valor      DECIMAL(10,2) NOT NULL CHECK (valor > 0),
  feito_em   DATE NOT NULL,
  CONSTRAINT fk_pedidos_cliente
    FOREIGN KEY (cliente_id) REFERENCES clientes(id)
    ON DELETE RESTRICT
);

Use utf8mb4: ele aceita acentos e emojis. O antigo "utf8" do MySQL não aceita todos.

Alterar uma tabela que já existe

ALTER TABLE clientes ADD telefone VARCHAR(20);
ALTER TABLE clientes MODIFY cidade VARCHAR(100);
ALTER TABLE clientes RENAME COLUMN telefone TO celular;
ALTER TABLE clientes DROP COLUMN celular;
RENAME TABLE clientes TO compradores;

MODIFY reescreve a coluna inteira: se você esquecer o NOT NULL ou o DEFAULT, eles somem. O RENAME COLUMN é do MySQL 8. Em versões antigas, use CHANGE.

DELETE vs TRUNCATE vs DROP

ComandoO que apagaDetalhe
DELETE FROM t WHERE ...Linhas escolhidasDML. Dá para desfazer em transação e dispara triggers.
TRUNCATE TABLE tTodas as linhasDDL. Rápido, zera o AUTO_INCREMENT, sem rollback. Falha se outra tabela tiver FK apontando para ela.
DROP TABLE tA tabela inteiraSome a estrutura e os dados.

2.2CRUD: criar, ler, atualizar, apagar

-- C: inserir (várias linhas de uma vez)
INSERT INTO clientes (nome, email, cidade)
VALUES ('Ana', 'ana@mail.com', 'Recife'),
       ('Bruno', 'bruno@mail.com', 'Natal');

-- R: consultar
SELECT nome, cidade FROM clientes
WHERE cidade = 'Recife';

-- U: atualizar
UPDATE clientes SET cidade = 'Olinda'
WHERE id = 1;

-- D: apagar
DELETE FROM clientes WHERE id = 2;

-- id gerado pelo último INSERT
SELECT LAST_INSERT_ID();

-- upsert: insere ou atualiza se o e-mail já existir
-- (sintaxe do MySQL 8.0.19+)
INSERT INTO clientes (nome, email)
VALUES ('Ana Lima', 'ana@mail.com') AS novo
ON DUPLICATE KEY UPDATE nome = novo.nome;

UPDATE e DELETE sem WHERE

UPDATE clientes SET cidade = 'Olinda'; muda todas as linhas da tabela.

Antes, rode um SELECT com o mesmo WHERE para ver o que vai mudar. No Workbench, o modo SET SQL_SAFE_UPDATES = 1; bloqueia esse erro.

2.3A ordem de uma consulta

Você escreve nesta ordem: SELECT→ FROM→ WHERE→ GROUP BY→ HAVING→ ORDER BY→ LIMIT
O banco executa nesta: 1FROM + JOIN→ 2WHERE→ 3GROUP BY→ 4HAVING→ 5SELECT→ 6ORDER BY→ 7LIMIT
  • Por isso um apelido criado no SELECT não funciona no WHERE (o WHERE roda antes), mas funciona no ORDER BY. No MySQL, também funciona no GROUP BY e no HAVING.
  • O DISTINCT é aplicado logo depois do SELECT, antes do ORDER BY.
  • O WHERE filtra linhas. O HAVING filtra grupos, depois do GROUP BY.

2.4Filtros com WHERE

OperadorExemplo
= <> != > < >= <=valor >= 100
BETWEENvalor BETWEEN 100 AND 500 (inclui as pontas)
INcidade IN ('Recife', 'Natal')
LIKEnome LIKE 'An%' → começa com "An"

AND, OR, NOTcidade = 'Recife' AND valor > 100
  • No LIKE, % é "qualquer coisa" e _ é "exatamente 1 caractere": '%silva', '_na'.
  • Maiúscula ou minúscula faz diferença? Depende da collation. Nas terminadas em _ci (case-insensitive, o padrão), 'ana' encontra 'Ana'.
  • email = NULL nunca dá verdadeiro. Use IS NULL.
  • Misturou AND com OR? Use parênteses: WHERE (a OR b) AND c.

2.5Ordenar, limitar e apelidar

-- sem repetição
SELECT DISTINCT cidade FROM clientes;

-- apelido (AS) e ordem alfabética
SELECT nome AS cliente FROM clientes
ORDER BY nome ASC;

-- os 5 maiores pedidos
SELECT * FROM pedidos
ORDER BY valor DESC LIMIT 5;

-- paginação: página 3, com 10 por página
SELECT * FROM pedidos
ORDER BY id LIMIT 10 OFFSET 20;

ASC = crescente (padrão), DESC = decrescente. Dá para ordenar por várias colunas: ORDER BY cidade, nome.

OFFSET alto fica lento, porque o banco lê e descarta as linhas puladas. Em tabelas grandes, pagine pela chave: WHERE id > ultimo_id ORDER BY id LIMIT 10.

2.6Agregação e GROUP BY

FunçãoRetorna
COUNT(*)Quantidade de linhas
COUNT(coluna)Quantidade de valores não NULL
SUM(valor)Soma
AVG(valor)Média
MIN / MAXMenor e maior valor
COUNT(DISTINCT col)Quantidade de valores diferentes
GROUP_CONCAT(nome)Junta os textos do grupo: 'Ana,Bruno'
 
-- cidades com mais de 10 clientes em 2026
SELECT cidade, COUNT(*) AS total
FROM clientes
WHERE criado_em >= '2026-01-01'
GROUP BY cidade
HAVING COUNT(*) > 10
ORDER BY total DESC;

Regra: toda coluna do SELECT que não está numa função de agregação precisa estar no GROUP BY. O MySQL cobra isso com o modo ONLY_FULL_GROUP_BY, ligado por padrão. SUM, AVG, MIN e MAX ignoram os NULL.

2.7Subconsultas e UNION

-- clientes que já compraram
SELECT nome FROM clientes
WHERE id IN (SELECT cliente_id FROM pedidos);

-- pedidos acima da média
SELECT * FROM pedidos
WHERE valor > (SELECT AVG(valor) FROM pedidos);

-- clientes sem nenhum pedido (correlacionada)
SELECT c.nome FROM clientes c
WHERE NOT EXISTS (
  SELECT 1 FROM pedidos p WHERE p.cliente_id = c.id
);

-- juntar resultados de duas consultas
SELECT email FROM clientes
UNION
SELECT email FROM fornecedores;
  • UNION remove duplicatas. UNION ALL mantém tudo e é mais rápido.
  • As duas consultas precisam ter o mesmo número de colunas, com tipos compatíveis.
  • Cuidado com NOT IN: se a subconsulta devolver algum NULL, o NOT IN não retorna nenhuma linha. Prefira NOT EXISTS.

2.8JOINs: juntando tabelas

INNER JOINsó o que existe nas duas
LEFT JOINtudo de A + o que combinar de B
RIGHT JOINtudo de B + o que combinar de A
FULL JOINtudo das duas (MySQL não tem: use UNION) 
-- A = clientes c, B = pedidos p
SELECT c.nome, p.valor, p.feito_em
FROM clientes c
INNER JOIN pedidos p ON p.cliente_id = c.id;

-- clientes sem pedido: LEFT JOIN + IS NULL
SELECT c.nome
FROM clientes c
LEFT JOIN pedidos p ON p.cliente_id = c.id
WHERE p.id IS NULL;
-- FULL JOIN no MySQL:
-- LEFT JOIN + só as sobras do RIGHT JOIN
SELECT c.nome, p.valor
FROM clientes c LEFT JOIN pedidos p ON p.cliente_id = c.id
UNION ALL
SELECT c.nome, p.valor
FROM clientes c RIGHT JOIN pedidos p ON p.cliente_id = c.id
WHERE c.id IS NULL;
  • JOIN sozinho é o mesmo que INNER JOIN.
  • Armadilha: num LEFT JOIN, o filtro da tabela da direita vai no ON. No WHERE, ele descarta as linhas sem par e o LEFT vira INNER.
  • CROSS JOIN: combina cada linha de A com cada linha de B (3 × 4 = 12 linhas).
  • SELF JOIN: a tabela com ela mesma, como funcionário e chefe na mesma tabela.
  • Onde não houver par, as colunas do outro lado aparecem como NULL.

3.1Índices

Funcionam como o índice de um livro: o banco acha a linha sem ler a tabela inteira.

CREATE INDEX idx_pedidos_cliente ON pedidos (cliente_id);
CREATE UNIQUE INDEX idx_clientes_email ON clientes (email);
SHOW INDEX FROM pedidos;
DROP INDEX idx_pedidos_cliente ON pedidos;

-- o banco vai usar o índice?
EXPLAIN SELECT * FROM pedidos WHERE cliente_id = 7;
  • No EXPLAIN, type = ALL quer dizer que ele leu a tabela toda. ref, eq_ref ou const quer dizer que usou índice.
  • Indexe colunas usadas em WHERE, JOIN e ORDER BY. A PK já vem indexada.
  • Índice acelera a leitura, mas deixa INSERT e UPDATE um pouco mais lentos.
  • LIKE '%ana' (com % no começo) não usa o índice.
  • Índice composto (cidade, nome) serve para filtrar por cidade, ou por cidade e nome. Só por nome, não: ele é lido da esquerda para a direita.
  • Função na coluna também anula o índice. Troque WHERE YEAR(feito_em) = 2026 por WHERE feito_em >= '2026-01-01' AND feito_em < '2027-01-01'.
  • No InnoDB, toda FK precisa de índice. Se não existir, o MySQL cria um sozinho.

3.2Transações e ACID

Um grupo de comandos que acontece inteiro ou não acontece.

START TRANSACTION;
UPDATE contas SET saldo = saldo - 100 WHERE id = 1;
UPDATE contas SET saldo = saldo + 100 WHERE id = 2;
COMMIT;      -- grava tudo
-- ROLLBACK; -- ou desfaz tudo, se algo falhou
LetraSignifica
AAtomicidade: tudo ou nada.
CConsistência: as regras (FK, CHECK) continuam valendo no fim.
IIsolamento: transações ao mesmo tempo não se atrapalham.
DDurabilidade: depois do COMMIT, fica gravado mesmo se a luz cair.
  • No MySQL, transação funciona no motor InnoDB (o padrão).
  • O autocommit vem ligado: fora de uma transação, cada comando é gravado na hora.
  • Comandos DDL (CREATE, ALTER, DROP) fazem commit automático, mesmo no meio de uma transação.
  • SAVEPOINT etapa1; cria um ponto de volta. ROLLBACK TO etapa1; desfaz só até ali.
  • O nível de isolamento padrão do InnoDB é REPEATABLE READ.

3.3Views

CREATE VIEW vw_clientes_recife AS
SELECT id, nome, email
FROM clientes
WHERE cidade = 'Recife';

SELECT * FROM vw_clientes_recife;

CREATE OR REPLACE VIEW vw_clientes_recife AS ...;
DROP VIEW IF EXISTS vw_clientes_recife;
  • View é uma consulta salva com nome, usada como se fosse tabela.
  • Não guarda dados: roda a consulta toda vez. O MySQL não tem view materializada (o PostgreSQL tem).
  • Serve para esconder consultas complexas e colunas sensíveis de quem só precisa ler.

3.4Stored procedures

DELIMITER $$
CREATE PROCEDURE pedidos_do_cliente(IN p_id INT)
BEGIN
  SELECT * FROM pedidos
  WHERE cliente_id = p_id
  ORDER BY feito_em DESC;
END $$
DELIMITER ;

CALL pedidos_do_cliente(1);
DROP PROCEDURE IF EXISTS pedidos_do_cliente;
  • Procedure = bloco de SQL guardado no banco e chamado pelo nome, com parâmetros IN, OUT ou INOUT.
  • O DELIMITER troca o ";" por "$$" enquanto você escreve, para o bloco inteiro ser um comando só.
  • FUNCTION é parecida, mas devolve um valor e pode ser usada dentro do SELECT.

3.5Triggers (gatilhos)

-- registra toda mudança de preço
CREATE TRIGGER trg_log_preco
AFTER UPDATE ON produtos
FOR EACH ROW
INSERT INTO log_precos (produto_id, preco_antigo, preco_novo, alterado_em)
VALUES (OLD.id, OLD.preco, NEW.preco, NOW());

-- BEFORE: corrige preço negativo para 0
CREATE TRIGGER trg_preco_minimo
BEFORE UPDATE ON produtos
FOR EACH ROW
SET NEW.preco = GREATEST(NEW.preco, 0);

DROP TRIGGER IF EXISTS trg_log_preco;
  • Roda sozinho BEFORE ou AFTER um INSERT, UPDATE ou DELETE.
  • OLD = a linha antes da mudança. NEW = a linha depois.
  • No BEFORE dá para corrigir o NEW antes de gravar. Para recusar a operação, use SIGNAL SQLSTATE '45000' dentro de um bloco BEGIN ... END.
  • Use com moderação: lógica escondida no banco é difícil de depurar.

3.6CTE e window functions

-- ranking de clientes por total comprado
WITH totais AS (
  SELECT cliente_id, SUM(valor) AS total
  FROM pedidos
  GROUP BY cliente_id
)
SELECT c.nome, t.total,
       RANK() OVER (ORDER BY t.total DESC) AS posicao
FROM totais t
JOIN clientes c ON c.id = t.cliente_id;
  • WITH (CTE) dá nome a uma subconsulta e deixa a leitura em etapas.
  • OVER (...) calcula sobre um grupo de linhas sem juntá-las numa só, como o GROUP BY faria.
  • Mais usadas: ROW_NUMBER(), RANK(), DENSE_RANK(), LAG(), LEAD() e SUM() OVER (PARTITION BY ...).
  • Disponível a partir do MySQL 8.0.

SHOW GRANTS FOR 'app'@'localhost';

ALTER USER 'app'@'localhost' IDENTIFIED BY 'nova_senha';

DROP USER 'loja_app'@'localhost';

3.8Backup e restauração

# no terminal, não dentro do mysql>
# backup de um banco
mysqldump -u root -p --single-transaction --routines --events loja > loja_2026-11-14.sql

# todos os bancos
mysqldump -u root -p --all-databases > tudo.sql

# restaurar (o banco precisa existir antes)
mysql -u root -p -e "CREATE DATABASE IF NOT EXISTS loja"
mysql -u root -p loja < loja_2026-11-14.sql
  • --single-transaction faz o backup do InnoDB sem travar as tabelas.
  • Procedures e events só entram com --routines e --events. Triggers já vão por padrão.
  • Guarde uma cópia fora do servidor.
  • Teste a restauração. Backup que nunca foi restaurado pode não funcionar quando você precisar.

3.9SQL Injection

Acontece quando o texto digitado pelo usuário vira parte do comando SQL.

// ERRADO: concatenando texto
"SELECT * FROM usuarios WHERE email = '" + email + "'"
// se email for:  ' OR '1'='1
// a consulta devolve TODOS os usuários

// CERTO: prepared statement (parâmetro ?)
query("SELECT * FROM usuarios WHERE email = ?", [email])
  • Sempre use parâmetros (prepared statements) ou um ORM. Nunca monte SQL somando strings.
  • O usuário do app deve ter só os privilégios que precisa. Nunca conecte como root.
  • Parâmetros protegem valores, não nomes de tabela ou coluna. Se o usuário escolhe a coluna de ordenação, compare com uma lista fixa de nomes permitidos.
  • Guarde senhas com hash (bcrypt, argon2), nunca em texto puro.

3.11Boas práticas

  • Todo UPDATE e DELETE com WHERE. Teste o WHERE antes com um SELECT.
  • Mudanças em várias tabelas dentro de uma transação.
  • DECIMAL para dinheiro e utf8mb4 para texto.
  • Datas gravadas em UTC. Converta para o fuso do usuário só na hora de mostrar.
  • Explorando uma tabela grande? Sempre com LIMIT.
  • Nomes em snake_case, sem acento e sem espaço. Escolha plural ou singular para as tabelas e mantenha o padrão.
  • Evite SELECT * no código do app: liste as colunas que precisa.
  • Índice nas colunas de busca e nas FKs. Confira com EXPLAIN.
  • Usuário do app com o mínimo de privilégios. Nunca root.
  • Backup automático e restauração testada.
  • Versione o esquema com migrations no Git, junto com o código.
